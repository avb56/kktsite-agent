# kktsite-agent — локальный сервер кассы

Сервер на Node на кассовом ПК. Для кассы выглядит как **«АТОЛ. Web Requests»**:
в настройках ККТ она подключается типом «Атол Сервер» по адресу
`http://<пк>:16732/api/v2/`, логин и пароль — в самом адресе
(`http://имя:пароль@<пк>:16732/api/v2/`), если учётки заведены. Зачем он
нужен и что решено — план kktsite (`docs/plan/kktsite.json` в репозитории
claude-test, раздел «Локальный компонент»). Касса и кабинет — там же; здесь
только агент.

Отличия от Web Requests:
- несколько ККТ на одном ПК;
- не нужна лицензия на сервер в ККТ;
- авторизация необязательна: пока не заведено ни одной учётки, агент открыт;
- в ответах /devices есть `lastError` — почему ККТ не подключилась.

## Что нужно на ПК

- **Драйвер ДТО 10 от Атола** — ставится инсталлятором Атола, с агентом не
  связан. Агент загружает установленный драйвер сам (обёртка
  [avb56/node-atol-wrapper](https://github.com/avb56/node-atol-wrapper) ищет его
  так же, как обёртки Атола) и работает с его версией.
- С ДТО 10.10.8.0 драйвер работает только при запущенной службе **АТОЛ Connect
  (UEM)** — её ставит инсталлятор Атола. Без неё подключение ККТ вернёт
  «Для работы с драйвером необходимо запустить службу UEMA». В следующем
  выпуске драйвера (с поддержкой ПИоТ) UEM, по словам пользователя (02.10.2026),
  убран, вместо него — три другие службы; агент с ним работает (Win7 x86).
- Поставили или обновили драйвер — **перезапустить сервер**: драйвер
  загружается при запуске. Кнопка на странице настроек (вкладка «Общие» и в
  предупреждении о драйвере), если агент работает службой.
- Node 20+ и, для установки зависимостей, инструменты сборки нативных модулей
  (python, make, компилятор C++): обёртка собирается при `npm install`.

## Установка на кассовый ПК

Со страницы загрузки `https://dl.kktsite.ru/agent/` (`packaging/site/index.html`,
nginx — `docs/deploy/nginx-dl.conf` в claude-test). Все выпуски —
[GitHub Releases](https://github.com/avb56/kktsite-agent/releases):

- **Windows** — `kktsite-agent-<версия>-windows.zip`, обе разрядности
  (`x64/`, `ia32/`). 64-разрядный процесс не загрузит 32-разрядный драйвер
  Атола и наоборот, поэтому `install.cmd` (на 32-битном node — идёт на любой
  Windows) смотрит в реестре, какой драйвер стоит (`src/winreg.js`), и ставит
  ту же разрядность; `--arch x64|ia32` — выбрать руками. Windows-сборки — на
  Node 22 LTS: последний с 32-битной сборкой под Windows (поддержка до 04.2027).
  zip собирает свой писатель (`scripts/zip.mjs`) — его открывает Проводник.
- **Windows 7** — `kktsite-agent-<версия>-windows7.zip`, тоже обе разрядности.
  Node 22 на Win7 не запускается («EventSetInformation не найдена в
  ADVAPI32.dll» — функция Windows 8+), поэтому эта сборка — на Node 12.22,
  последнем, что идёт на Win7 (`IsWindows7OrGreater` в его `node_main.cc`).
  Код агента тот же: `pack.mjs --bundle-node12` собирает его esbuild в один
  CommonJS-файл под node12, обёртка драйвера — под заголовки Node 12,
  обновляется по своей платформе (`windows7-x64` / `windows7-ia32`). На Win7
  нужен Universal CRT (KB2999226) — им пользуется и драйвер Атола. Node 12 без
  обновлений безопасности с 04.2022 — для касс в закрытой сети.
  Чего в общем коде поэтому нет: `fs.rmSync` и `stream/promises` (`src/fsx.js`),
  `fetch`, `X509Certificate` (сведения о сертификате — `agent-cert.json`),
  `await` на верхнем уровне, `Get-CimInstance` (PowerShell 2.0 на Win7).
- **Linux, macOS** — `kktsite-agent-<версия>-<платформа>.tar.gz`.

Внутри — свой node, агент со собранной обёрткой драйвера (без библиотек
Атола), `install.*`, `uninstall.*`, README.txt.

```bash
sudo ./install.sh --port 16732        # Linux, macOS
install.cmd --port 16732              # Windows, от имени администратора
```

Ставит в `/opt/kktsite-agent` (macOS — `/usr/local/kktsite-agent`, Windows —
`%ProgramFiles%\kktsite-agent`) и запускает службой (см. «Автозапуск»):

```
<корень>/current → versions/<версия>
<корень>/versions/<версия>/{node, app}
```

**Самообновление** (`src/update.js`): раз в сутки агент читает
`https://dl.kktsite.ru/agent/latest.json` (адрес задаётся при сборке, `pack.mjs`) и его подпись ed25519 —
открытый ключ зашит в агент, закрытый только у выпускающего. Версия новее —
скачивает архив своей платформы (`windows-x64` / `windows-ia32` / …), сверяет
sha256 из подписанного `latest.json`, распаковывает в `versions/<новая>`,
запускает пробно (`main.js --version`: версия и нативная обёртка), ждёт, пока
очереди ККТ опустеют, переключает `current` и завершается — служба поднимает
новую версию. Предыдущая остаётся для отката. Выключить или обновить сейчас —
на странице настроек, вкладка «Обновление».

Проверено на Debian 13 (29.09.2026): установка из архива, обновление
0.2.0 → 0.3.0 по кнопке и само (через минуту после запуска), ККТ снова
подключилась, удаление.

## Выпуск

1. Поднять версию в `package.json`, закоммитить.
2. Actions → **agent-release** → Run workflow: архивы linux-x64, windows-x64,
   windows-ia32, windows7-x64, windows7-ia32, macos-arm64, macos-x64 — на
   каждой платформе установка из архива и проверка службы; затем Windows-zip
   для 10/11 и для 7. Итог:
   - **GitHub Release `v<версия>`** с архивами и `SHA256SUMS` — архив всех
     выпусков. Та же версия второй раз не выпустится (тег уже есть);
   - артефакт `kktsite-agent-release` — скачать (попадёт в `~/Загрузки`).
3. Подписать и выложить одной командой (ключ подписи — только на этой машине):
   ```bash
   scripts/agent-ship.sh --ship kkt@prod     # артефакт — самый новый в ~/Загрузки
   scripts/agent-ship.sh --dry-run           # только распаковать, подписать, показать
   ```
   Соединение с узлом одно (пароль — один раз), файлы — через `tar | ssh`,
   на узле ничего ставить не нужно. Кладёт в `/srv/kkt/static/agent`
   (`--dir` — другой каталог стека). Корень dl.kktsite.ru — страница разделов
   загрузок — не забота агента: она в claude-test (`docs/deploy/dl/`). Та же
   версия с другой сборкой уже на узле — остановится, ничего не меняя.

   На узле остаётся **только текущий выпуск** — его берут агенты для
   обновления, и только он попадает в полную копию узла. Прежние выпуски с
   узла убираются, но лишь те, что лежат в GitHub Release своей версии байт в
   байт (sha256 из API GitHub, без токена); остальные остаются, и скрипт их
   называет. `--no-prune` — не убирать ничего.

   Подписанный `latest.json` с подписью уходит в GitHub Release этой версии,
   если на машине есть `gh` с входом (`gh auth login`); иначе скрипт печатает
   команду.

   Ключ — `~/.config/kktsite-agent-release/signing-key.pem`
   (`agent-release.mjs keygen`, один раз; уже выпущен). Потеряли — агенты
   новые обновления не примут, переставлять установщиком.
4. Один раз на сервере — сайт `docs/deploy/nginx-dl.conf` из claude-test
   (dl.kktsite.ru: страница загрузки, самообновление, `/agent/archive/` →
   GitHub Releases). Отдельный том не нужен: `/srv/kkt/static` балансиру уже
   смонтирован.

## Запуск из репозитория (разработка)

```bash
npm install
npm start            # или: node src/main.js
```

Переменные окружения:

| переменная | по умолчанию | что это |
|---|---|---|
| `KKT_AGENT_PORT` | 16732 | порт; на ПК с Web Requests нужен другой |
| `KKT_AGENT_HOST` | 0.0.0.0 | 127.0.0.1 — только этот ПК; 0.0.0.0 — общая касса по сети |
| `KKT_AGENT_DRIVER` | поиск | каталог или файл драйвера ДТО 10 |
| `KKT_AGENT_DATA` | каталог настроек ОС | `~/.config/kktsite-agent`, `%APPDATA%\kktsite-agent`, `~/Library/Application Support/kktsite-agent` |

### HTTPS

Нужен, только если браузер кассы не пускает её (страница по https) к
агенту по http. По умолчанию выключен. Включается на странице настроек
кнопкой «Выпустить сертификат и включить HTTPS»: агент выпускает
самоподписанный сертификат на `localhost`, имя ПК и его адреса в сети и сразу
слушает https на порту `KKT_AGENT_HTTPS_PORT` (по умолчанию http + 1). В кассе
адрес — `https://<пк>:16733/api/v2/` (для агента на 16732).

Сертификату доверяют один раз на кассовом ПК («Скачать сертификат» и
инструкция на странице). Это не удостоверяющий центр (`CA:FALSE`): подписать
им другой сайт нельзя. Сам агент сертификат не перевыпускает — появился
новый адрес ПК или подходит срок (825 дней), страница предложит
«Перевыпустить», и новому сертификату доверяют заново. Файлы — `agent.crt` и
`agent-key.pem` (0600) в каталоге данных.

### Автозапуск

Служба ОС: агент поднимается при загрузке ПК и перезапускается, если упал.
Ставится с правами администратора, из каталога агента, тем же node:

```bash
sudo "$(command -v node)" src/main.js service install --port 16733   # Linux, macOS
node src\main.js service install                                      # Windows, консоль администратора
node src/main.js service status
sudo "$(command -v node)" src/main.js service uninstall
```

Параметры: `--port`, `--https-port`, `--host`, `--driver` (не заданы — из `KKT_AGENT_*`
окружения, иначе по умолчанию), `--user` — от кого работает агент.

| ОС | как | от кого | данные и журнал |
|---|---|---|---|
| Linux | служба systemd `kktsite-agent` | `--user`, по умолчанию тот, кто вызвал sudo; root — нельзя | `~/.config/kktsite-agent`, `journalctl -u kktsite-agent` |
| Windows | задача планировщика `kktsite-agent` при старте системы, `run.cmd` с перезапуском | SYSTEM | `%ProgramData%\kktsite-agent`, `agent.log` там же |
| macOS | LaunchDaemon `ru.kktsite.agent` | `--user` | `~/Library/Application Support/kktsite-agent`, `agent.log` там же |

Служба запоминает путь к агенту и к node: перенесли каталог или обновили
node — `service install` заново (повторный install перезаписывает службу).
На Windows учётки агента службы лежат в `%ProgramData%`: перед
`users add` — `set KKT_AGENT_DATA=%ProgramData%\kktsite-agent`.

Проверено на Linux (Debian 13, systemd 257): установка, запуск от
пользователя, перезапуск после `kill -9`, удаление. На всех трёх ОС это же
гоняет GitHub Actions (`.github/workflows/agent.yml`, скрипт
`scripts/ci-service-check.mjs`) — на каждый push (кроме правок `*.md`) и вручную.

Учётные записи (basic-авторизация) — на странице настроек, вкладка «Доступ» →
«Доступ к серверу», или с консоли:

```bash
node src/main.js users add <имя> <пароль>   # первая учётка включает авторизацию
node src/main.js users list
node src/main.js users del <имя>
```

## ККТ

Страница настроек — `http://<пк>:16732/` (если заведены учётки, браузер
спросит логин и пароль): список ККТ, добавление и настройка, подключение и
отключение, «Проверить связь» (модель, заводской номер, прошивка), ККТ по
умолчанию, адрес для кассы у каждой ККТ, срок хранения заданий.

ККТ выбирает параметр `deviceID`: в кассе адрес «Атол Сервер»
`http://<пк>:16732/api/v2/?deviceID=2`, касса передаёт его и с заданием, и с
опросом результата. Без `deviceID` — ККТ **по умолчанию** (её меняют на
странице или `setDefaultDevice`); первая добавленная ККТ — по умолчанию сразу.

То же через API, в формате Web Requests — настройки подключения можно
переносить между ними как есть:

```bash
curl -X POST http://127.0.0.1:16732/api/v2/devices -H 'Content-Type: application/json' \
  -d '{"id":"1","name":"Atol30","connectionSettings":{"model":500,"port":"usb","usbDevice":"auto"}}'
curl -X POST 'http://127.0.0.1:16732/api/v2/activateDevice?deviceID=1'
curl -X POST http://127.0.0.1:16732/api/v2/setDefaultDevice -H 'Content-Type: application/json' -d '{"id":"1"}'
```

Подключённые ККТ подключаются снова при следующем запуске агента. ККТ
платформы 5 (проверено на АТОЛ 30Ф) подключаются по USB — `"port":"usb"`, не
через `/dev/ttyACM*`.

## API

`/api/v2`: `serverInfo`, `settings`, `devices` (`devices/default`),
`setDefaultDevice`, `utils/mapping`, `utils/deviceParametersStruct`,
`activateDevice` / `deactivateDevice`, `requests` (POST, GET/DELETE по uuid),
`getRequestsQueueStatus`, `operations/query*` (через JSON-задания драйвера).
Коды, статусы задач (`wait`, `inProgress`, `ready`, `error`, `interrupted`,
`canceled`) и тексты ошибок сверены с настоящим Web Requests 1.0.4.0 —
подробности в `src/device.js`. Его спецификацию он сам отдаёт по адресу
`http://<пк>:16732/docs/openapi.yaml`.

Блокировка очереди — как у Web Requests (подробно — `src/device.js`):
- связь с ККТ или обмен с ФН оборвались посреди фискального документа —
  задача `blocked`, очередь стоит (`isBlocked`, `blockReason`,
  `blockedUUID`). Агент раз в 3 с проверяет ККТ и по номеру последнего ФД
  (запоминается перед задачей) решает: закрылся — `ready` (результат — только
  номер ФД) и допечатка, не закрылся — `error`. Очередь идёт дальше;
- с `blockQueueOnPrintErrors` так же ждёт бумагу: чек закрыт, но не
  допечатан — очередь стоит, пока бумагу не вставят.

Касса на `blocked` продолжает ждать результат.

Ещё не как у Web Requests:
- состояние очереди живёт в памяти: перезапуск агента во время блокировки
  её теряет;
- `validateRequestsOnAdd`, скрипты ДТО, доп. строки документа и
  `otherSettings` хранятся, но пока ни на что не влияют.

## Проверка

```bash
npm test             # на подложном драйвере, без ККТ
```

На настоящей ККТ: одно USB-устройство открывает кто-то один — если на ПК
работает Web Requests с этой ККТ, сначала освободить её
(`POST /api/v2/deactivateDevice` у него), потом подключить к агенту, после
проверки — наоборот.
